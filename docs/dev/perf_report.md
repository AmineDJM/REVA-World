## Caveats (read before citing these numbers)

- **Not the reference hardware.** Render plans are API 0.5 CPU/512 MB, worker 1 CPU/2 GB and PostgreSQL 0.1 CPU/256 MB. Here `taskset -c 0` gives the API and the measured processes one *full* core; the API is additionally measured under an emulated 0.5 CPU quota (SIGSTOP/SIGCONT, not a cgroup, so throttling granularity differs from Render's), memory is not capped (no cgroup limit was applied; the 2 GiB budget is checked only against measured peak RSS), and PostgreSQL runs in a local Docker container with unconstrained CPU on the same host and no network latency. Expect slower API/DB numbers on Render.
- **Single run.** Percentiles come from one measurement session on a shared machine where other processes (parallel agents, test suites) were running; see the load averages above.
- **Small data.** The database holds only captured test fixtures (four countries, few concepts), so query latencies do not reflect a larger live corpus.
- **Cached metadata is not cached.** No application/HTTP cache exists for `/v1/ontology` or `/v1/sources`; the measured values are server-side uncached latency (an upper bound for a cached path).
- **Four-country numbers are synthetic.** The labelled benchmark fixture is used only for the numerical timing; the live scenario uses the three verified countries (DZA crude flows are typed Missing in live data).
- **Queue acknowledgement** is measured for an idle worker with concurrency 1; with a long job occupying the only slot, acknowledgement waits for that job (by design).
